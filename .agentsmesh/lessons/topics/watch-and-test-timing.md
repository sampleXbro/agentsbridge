# Lessons: watch & test timing

## Rules (apply unconditionally)

1. In tests, import `runWatch` from `tests/harness/watch.js` — never from `src/cli/commands/watch.js` directly; mock the production module path separately while keeping the harness import. (Evidence: L9)
2. Watch tests that mutate files after `runWatch()` must first wait for an initial generated artifact or log signal, then perform the edit and wait for the expected reaction — never assume the watcher is past its initial generation/readiness phase under full-suite scheduler load. (Evidence: L29, L89)
3. `runWatch()` must wait for the chokidar `ready` event before doing the initial reconciliation/generate; verify both the isolated watch suite and full `pnpm test` after any watcher-startup change. (Evidence: L89)
4. Watch-mode ignore filters must suppress both exact generated files (e.g. `.agentsmesh/.lock`, `.agentsmesh/.lock.tmp`) AND the canonical parent directory event emitted when those bookkeeping files churn; validate with the isolated watch suite and the full `pnpm test` run. (Evidence: L90, L117)
5. After bumping any test-runner or watcher-adjacent dependency (e.g. Vitest 4.0.x → 4.1.x), rerun the full suite and increase watch-unit `vi.waitFor` budgets again if needed — isolated green runs are not enough. (Evidence: L74)
6. Keep watch unit `vi.waitFor` timeouts comfortably above 3000 ms (for example 8000 ms) and idle-stability delays at least 3000 ms — `pnpm test:coverage` slows chokidar debounce + generate past short budgets even when plain `pnpm test` is green. (Evidence: L167)
7. Any watcher test must create a fresh temp project directory per test case; never reuse a prior watched path after teardown — shared temp dirs leak chokidar state under coverage load. (Evidence: L85)
8. Never run test commands in parallel when they touch the same temp paths, ports, caches, or repo artifacts (e.g. fixed `ab-watch-cmd-test`). (Evidence: L112)
9. Watch tests that prove event-driven behavior must keep the watcher in a `finally` cleanup and retry the triggering write until the observed callback fires or the normal timeout expires — chokidar may miss a lone create event under full-suite saturation. (Evidence: L189)
10. When a watch test needs to wait for "the next regen cycle", thread an `onCycle({ featuresChanged })` callback into `runWatch` and assert on `cycles.length`/`cycles[i].featuresChanged` — never scrape `infoSpy.toHaveBeenCalledWith('Regenerated.')` or other externally-observable log/spy side-effects (the startup generate already fires them, producing tautological waits). Keep `scripts/flake-check-watch.ts` (N=10 under `COVERAGE=1`) and `pnpm flake:watch` wired in `package.json` to validate stability whenever the watch loop changes. (Evidence: L254)
11. Any test that creates a watch then writes into a just-created subdirectory must force chokidar's polling backend (`usePolling: true, interval: 50`) via `tests/harness/watch.ts` rather than rely on native `fs.watch` — macOS FSEvents and Linux inotify drop events on freshly-added subtrees under parallel scheduler load. Keep production native for real interactive use; never trust kernel event delivery in parallel test environments. (Evidence: L266)
12. Keep e2e CLI helper timeouts (e.g. `runCli` 30s) high enough for full-suite parallel pressure; reproduce timeout-looking failures both targeted and under the full runner before treating them as product behavior failures. (Evidence: L53)
